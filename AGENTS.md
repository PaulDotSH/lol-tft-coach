# Agent instructions

## Project

LoL Coach: a Windows second-monitor desktop coach for League of Legends (and a
TFT mode). Champ select picks/bans/builds, in-game item advice and threat board,
ARAM Mayhem augment ranking read off the screen by OCR, game review, and an
optional click-through overlay that never takes focus. It is read-only: Riot's
local APIs, public stats sites, and screen reading. Personal-use app, in active
development; remote is github.com/PaulDotSH/lol-tft-coach (branch `master`).

- Spec: `docs/superpowers/specs/`; future ideas: `docs/ideas.md`.
- Mayhem is a main mode. The app is silent and shows ranks, never win rates, for
  augments.
- Don't restart the running app mid-game unless asked (it loses the recap's game
  log). Don't test by stealing focus or clicking over the user's windows.

## Stack and layout

- Tauri 2 desktop app: Rust workspace (edition 2024, `crates/*` plus `src-tauri`)
  and a Svelte 5 + Vite + TypeScript UI in `web/` (npm).
- `src-tauri` (package `lol-coach`): app entry, phase loop (`orchestrator.rs`),
  TFT loop (`tft.rs`), native overlay windows (`overlay/`), commands, tray.
- `crates/model` re-exports `model-core/static/game/live/draft/review`: shared
  types. `data`: Data Dragon, lolalytics, u.gg, Coachless, disk cache (hand-written
  `champ_notes.toml`, `matchup_notes.toml`, `traits.toml`). `clients`: League
  client (LCU) and Live Client API. `coach`: pure decisions, tuning in
  `consts.rs`, `modes.toml`, `augments.toml`. `ocr`: GDI capture + Windows OCR.
  `tft-model/data/coach/vision/embed/choncc`: the TFT side.
- `web/src`: dashboards; mock mode when opened outside Tauri.
- Generated, do not edit by hand: `web/src/lib/bindings/` and `tft-bindings/`
  (ts-rs output, regenerated by `cargo test --workspace`), `src-tauri/gen/`,
  `target/`, `web/dist/`.
- Runtime files live under `%APPDATA%\lol-coach` and `%LOCALAPPDATA%\lol-coach`
  (settings, caches, logs, debug dumps, Coachless tokens). Never commit them.

## Commands

- Install: `npm --prefix web install`
- Run: `run.cmd` (builds if needed); `run.cmd debug` (verbose log and dumps);
  `run.cmd build` (rebuild then start).
- Dev (hot reload): `web\node_modules\.bin\tauri dev`; UI only in mock mode:
  `npm --prefix web run dev`.
- Build: `web\node_modules\.bin\tauri build --no-bundle` (output
  `target\release\lol-coach.exe`).
- Test: `cargo test --workspace`; web: `npm --prefix web test`.
- Typecheck: `npm --prefix web run check`.
- Real data through the coach, no UI or game: `cargo run -p lol-coach --example smoke`.

Run the relevant checks before declaring work done.

## Coding style and rules

- Follow existing patterns and match the surrounding code.
- Do not over-rely on OOP when a simpler structure fits.
- Do not add helper functions when an equivalent already exists in a library
  that is already in use.
- Prefer the standard library and existing dependencies over new ones.
- Do not add comments unless asked.
- The repo has no rustfmt.toml and is hand-formatted wide. Never run `rustfmt` or
  `cargo fmt`.
- `coach` stays pure (no I/O); network and OS access belong in `data`, `clients`,
  `ocr` and `src-tauri`.
- Commit or push only when asked. Never add AI co-author trailers (e.g.
  `Co-Authored-By: Claude`) to commits.
- Parallel worktrees (`apps/lol-coach-wt/`) share one cargo build-dir; give each
  its own `CARGO_BUILD_BUILD_DIR` or crates compile against a stale `model`.
- `crates/tft-choncc` is for the temporary Choncc or Treat queue (1230) and is to
  be deleted after 2026-11-17.

## Testing and verification

- Write tests before implementation where practical.
- When a test fails, fix the code — not the test — unless the test asserts the
  wrong behavior. Never weaken a test just to make it pass.
- Static types, linters, and checkers are part of "done".
- Parsers are tested against saved real responses in `fixtures/`; add a fixture
  when fixing a parsing bug. Without a game, serve
  `fixtures/clients/live_allgamedata.json` over HTTPS on 127.0.0.1:2999 or use
  `cargo run -p ocr --example fake_league`.

## Output-heavy commands

- **Delegate output-heavy commands to a cheap model.** When a command's output
  is large but the answer you need is small (parsing logs, sifting build or CI
  output, scanning long dumps), prefer handing it to a cheap subagent and
  taking back only the conclusion: DeepSeek via the `deepseek` MCP
  (`run_task`) or Claude Haiku. Give it the exact command and what to report;
  it reads, it does not edit. This needs no explicit opt-in.
- **Test runs print failures, not passes.** Run suites in a mode that hides
  passing tests and shows only failures plus the summary: e.g. `cargo test -q`,
  `cargo nextest run --status-level fail`, `pytest -q`, `vitest --reporter=dot`,
  `go test ./...` without `-v`, `dotnet test -v q`. If the runner has no such
  mode, filter its output down to the failures. Never pull hundreds of passing
  lines into context.

## Planning

- For large tasks, plan first with a strong model, then implement with cheaper
  models to save tokens.
- State the goal and the stopping condition before starting.

## Subagent usage

These rules are always in effect, even when the `dispatching-parallel-agents`
skill is not loaded. If you do dispatch subagents, follow them; the skill has
the full workflow.

- **Explicit opt-in only.** Never dispatch, spawn, or delegate to subagents
  unless the developer explicitly asks for it in the current task (e.g. "use
  subagents", "dispatch these in parallel", "delegate this"). A task looking
  parallelizable is not authorization, and neither is a past instruction. If
  parallel work would clearly help, ask once; absent a yes, do the work yourself,
  sequentially. Exception: delegating an output-heavy command to a cheap model
  (see "Output-heavy commands") needs no opt-in.
- **Cheap models for subagents.** The coordinating session runs the expensive
  model; helpers run a cheap/fast one: ChatGPT Luna, DeepSeek v4.1 Flash, Claude
  Sonnet, or Muse-Spark. Pick the cheapest that can do the job, never silently a
  premium model, and state the chosen model in the dispatch and the summary.
- **Poll at the harness cadence.** Polling too often destroys prompt-cache
  retention. Claude Code: check every 4 minutes. Codex and opencode running
  OpenAI models: check every 25 minutes, otherwise wait for completion, and do
  not poll faster. Manual polling only — no tight auto-poll loops. If a result
  arrives earlier, use it immediately.
