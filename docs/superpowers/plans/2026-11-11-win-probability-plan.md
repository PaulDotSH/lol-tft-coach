# Plan: live win probability, state-aware items and posture

Spec: `docs/superpowers/specs/2026-11-11-win-probability-design.md` (approved 2026-11-11; read it first; this plan does
not repeat the feature table or the type shapes).
Goal: a calibrated win probability from the scoreboard, shown in game with its factors and
objective stakes; item scoring and a posture read that use it; the same curve in the game review.
Done when: the spec's stopping condition holds.

## Ground rules (every task)

- `AGENTS.md` applies in full. In particular: never `rustfmt` / `cargo fmt` (hand-formatted wide);
  no comments beyond the terse `///` and `//!` docs the neighbours have; constants at the top of
  the file or in `consts.rs`; `coach` stays pure (no I/O, no clock); no new dependencies when the
  standard library or an existing one does it.
- Tests first. Run quietly: `cargo test --workspace -q`, `npm --prefix web test`,
  `npm --prefix web run check`. A failing test means fix the code.
- `web/src/lib/bindings/` is generated by `cargo test --workspace`; never edit it by hand. New
  fields on existing structs are `#[serde(default)]` so old mock states and caches still load.
- Do not commit or push unless the user asks. No AI co-author trailers.
- Do not restart the running app during a game, never click or focus windows, no long CPU jobs
  while `League of Legends.exe` runs (check `tasklist`).
- Dev data lives outside the repo: `%LOCALAPPDATA%\lol-coach\dev\winprob\`. Only code, the fitted
  `winprob.toml` and small fixtures go in the repo. The Riot key and Coachless tokens are never
  printed, logged or committed.
- Python: `py -3.12 -I`, dependencies `requests numpy` only.
- No subagents unless the user asks for them in that session.
- When a fact below turns out wrong (an event name, a response field), stop, record what the
  real data shows in the spec's "Facts" section, and adjust the task; do not guess around it.

## Order

```
T0 spikes ─┬─ T1 live events ── T2 model eval ─┬─ T4 wire into advice ─┬─ T5 posture ──┐
           │                                   │                       ├─ T6 items ────┼─ T7 UI
           └─ T3 fitter (needs RIOT_API_KEY) ──┘                       └─ T8 review ───┘
                                               T9 ARAM / Mayhem table (after T3, T4)
```

T1 → T2 and T3 are independent. T4 can be built against an inline test table before T3 lands;
nothing is shown to the user until `winprob.toml` has `games > 0`.

Needs the user once: `RIOT_API_KEY` set (T0b, T3), and a Coachless sign-in in the app (T0a, T6b).

**c. Live events.** Over `%LOCALAPPDATA%\lol-coach\fixtures\allgamedata-*.json` list every

Done when: the spec's "Facts" section holds the answers and the fixtures are saved.

2. `live::parse` maps `TurretKilled`, `InhibKilled`, `InhibRespawned` before the generic `*Kill`

3. Tests on `fixtures/clients/live_allgamedata.json` (one turret, T2 side) and on a small added
   fixture with an inhibitor kill and respawn if T0c found one in the recordings.
4. Every `match` on `GameEvent` in the workspace still compiles and ignores the new variants
   unless stated here.

Done when: parser tests pass and `cargo test --workspace -q` is green with regenerated bindings.

## T2. The model, pure (`crates/coach/src/winprob.rs`, `crates/coach/winprob.toml`)

1. `winprob.toml` schema, loaded with `LazyLock` + `include_str!` like `modes.toml`:
   `patch`, `games`, `knots = [0, 10, 15, 20, 25, 30, 40]`, then per mode table (`[rift]`,
   `[aram]`) one array of knot values per feature key and a `[rift.metrics]` block (log loss,
   Brier, ECE, accuracy by minute). Ship it with `games = 0` and empty tables.
2. `State`: the feature vector. `State::from_snapshot(snap, sd, curves, my_team) -> State` builds
   it from a `GameSnapshot` (item gold through `common::inventory`, buffs from event times with
   durations in `consts.rs`, inhibitors down = killed and not respawned, `dead` from
   `Player::respawn_in`, `outlook` from `&HashMap<ChampKey, plan::Curve>`). Buff durations and the
   inhibitor respawn time are checked against the current patch before they go in.
3. `eval(table, &State, minute) -> f32` with knot interpolation; `win_prob(input) -> Option<WinProb>`
   producing `p`, `base`, `trend` (from `gold_history`), `factors`, `stakes`, `outlook`, `rough`,
   `source` exactly as the spec defines. None when the mode has no table or `games == 0`.
   Tests pass a table directly, so they do not depend on the shipped file.
4. Types `WinProb`, `WinFactor`, `Stake`, `Outlook` in `crates/model-live/src/lib.rs`;
   `GoldSample.win: Option<f32>`.
5. `State::from_frame(detail: &MatchDetail, frame_index) -> State` for the review (T8): same
   features from the LCU timeline, with `total_gold − current_gold` in place of item gold.
6. Tests in `crates/coach/tests/winprob.rs`: the list in the spec's "Testing" section, plus the
   parity test over `fixtures/coach/winprob_cases.json` (skipped while the file is absent).

Done when: the unit tests pass against an inline table and the module has no I/O.

## T3. Fitting tool (`tools/winprob/`)

Follows the spec's section 2. Files: `crawl.py`, `features.py`, `fit.py`, `README.md` (how to run,
in order, with the key in the environment).

1. `crawl.py`: resumable; a small on-disk queue of puuids and match ids; one sleep-based limiter
   for 100 requests / 2 min and a back-off on `429` (`Retry-After`). Region from an argument
   (default `euw1` / `europe`). Stops at `--games N`. Prints progress every 100 games.
2. `features.py`: timeline + match → rows `(game_id, minute, y, features…)` from blue's side,
   same definitions and constants as `winprob.rs` (keep one list of feature keys in each and a
   test that they match the TOML). Champion-by-length tables come from the training split only.
3. `fit.py`: hat basis over the knots, L2 logistic regression by Newton steps in numpy, equal
   weight per game, split by game id. Reports per 5-minute bucket: rows, log loss, Brier, ECE,
   accuracy, and the gold-only baseline beside them; a reliability table (10 bins); coefficient
   signs across five folds. Drops features with unstable signs and refits. Writes
   `crates/coach/winprob.toml` and `fixtures/coach/winprob_cases.json`.
4. Run it: 10k ranked solo games, Emerald+ on the current patch. If the gates in the spec fail,
   report the numbers and stop; do not ship the table.

Done when: `winprob.toml` has `games > 0`, the gates pass, and the Rust parity test passes.

## T4. Into the advice

Files: `crates/coach/src/lib.rs`, `crates/coach/src/gold.rs`, `src-tauri/src/orchestrator.rs`,
`src-tauri/examples/winprob_replay.rs`.

1. `GameInput` gains `curves: &HashMap<ChampKey, Curve>` and `income: Option<f32>`
   (`Tracker::income`). The orchestrator fills `curves` from `Shared::lengths` for the ten
   champions (the same lookups `game_plan` makes; do not fetch twice).
2. `game_advice` computes `win` early (before items, which T6 will feed) and stores it in
   `GameAdvice.win`; `gold_diff` writes `win` (the `base` value) into the sample it pushes.
3. `winprob_replay` example: groups the recorded `allgamedata-*.json` by game, runs
   `live::parse` + `win_prob`, prints one line per game (minutes, p at 10 / 15 / 20 / end, result
   when known) and a small reliability table over all snapshots with a known result.
4. Smoke example prints the win line for the live fixture.

Done when: the replay runs over the local recordings without a panic and the curves look sane by
eye (a stomp trends to one side; an even game stays near the middle), numbers reported.

## T5. Posture (`crates/coach/src/posture.rs`, `crates/coach/src/calls.rs`)

1. `Posture`, `Stance` in `model-live`; `GameAdvice.posture: Option<Posture>`.
2. `PostureMemo { stance, since }` with `decide(&mut self, win, advice, snap, sd) -> Posture`
   implementing the spec's table, the 3-point hysteresis and the 45 s dwell; constants in
   `consts.rs` (`POSTURE_*`). Kept in the orchestrator's `Memo` like `Tracker`, reset per game.
3. `why` and `options` are built only from facts already in the advice: `win.factors`,
   `win.outlook`, `win.stakes` with `timers`, `bounties`, `deaths`, `gold_eta`. Wording as in
   `plan.rs` and `readiness`: a read and choices, no bare orders.
4. `calls::readiness` rebased on `win` as the spec says, keeping today's rule as the fallback when
   `win` is None (existing `tests/calls.rs` must still pass for that path). Take calls append the
   stake's swing.
5. A stance change pushes one `Call` with key `stance-<stance>-<n>`; spoken only when
   `Settings::posture_calls` is on (new field, default false).
6. Tests in `crates/coach/tests/posture.rs`: one per table row, hysteresis, dwell, options from a
   state with a Baron stake and a named shutdown, None without `win`.

Done when: tests pass and the mock in-game state shows a posture that matches its numbers.

## T6. Items

**a. Standing and tempo** (`items.rs`, `needs.rs` call site in `lib.rs`, `consts.rs`):
`Standing` from `win.base`; `ctx.ahead` as the spec defines with the KDA rule as fallback; the
behind / ahead need scaling; the tempo term from `income` and the remaining cost
(`items::remaining_cost`), only when behind. New constants `STANDING_BEHIND`, `STANDING_AHEAD`,
`BEHIND_DEFENSE`, `AHEAD_DEFENSE`, `TEMPO_W`, `TEMPO_FREE_MIN`, `TEMPO_MAX`. Tests: existing item
tests unchanged with `win` None; a behind state lowers a far-off expensive item below a near one
of similar score; snowball items need `Standing::Ahead`.

**b. Coachless situations** (`crates/data/src/coachless.rs`, `crates/model-static`,
`src-tauri/src/orchestrator.rs`, `items.rs`):
1. `coachless::item_situations(http, auth, q, item, slot) -> anyhow::Result<ItemSituations>`
   parsing the T0a fixture (test on the saved reply). `ItemSituations { overall, by: Vec<(Situation, f32, f64)> }`,
   `Situation` the 15-value enum in the site's order.
2. A cache on `Shared` keyed by (champion, lane, item, slot), filled through `state::ensure`
   for at most six items per slot: last tick's Buy next, alternatives and the next two path items.
   Passed to the coach as `GameInput.situations: &HashMap<ItemId, ItemSituations>`.
3. `coach`: `situations::live(advice inputs) -> [Situation; 5]` maps the game to one situation per
   group (thresholds in `consts.rs`, taken from T0a where Coachless defines them). `score_all`
   adds the shrunk situation term to `score`, halves the `answers · needs` term for that item,
   and `Scored` carries the term so `reason` can say "better from behind (Coachless)".
4. Tests: the documented cases in the spec; no data → today's order; too few games in a
   situation → term 0.

Done when: both parts pass their tests and the smoke example shows the reason line for a signed-in
run (reported, not asserted).

## T8. Review

Files: `crates/model-review/src/lib.rs`, `crates/coach/src/analysis.rs`, the review components
under `web/src/components/idle/`.

1. `GoldPoint.win: Option<f32>` and `MatchAnalysis.swings` (spec section 5): live samples when
   the game was played with the app (`GameLog`), else `State::from_frame` per timeline frame.
2. Swings: the five largest changes between consecutive points, labelled from the kills and marks
   in that span (reuse `fights::fights` and `TimelineMark`).
3. Tests in `crates/coach/tests/analysis.rs` on `fixtures/clients/match_timeline.json`: a curve
   that ends on the winner's side, swings sorted and labelled.
4. UI: the win line on the review's gold chart and a swings list; `analysis.json` mock updated.
5. Later, only if asked: macro-coach "thrown leads" and "comebacks" patterns (`PastGame` gains
   the peak and low, cache version bump in `history.rs`).

Done when: a real past game opens in the review with the curve and swings.

## T9. ARAM and Mayhem

1. Crawl 5k ARAM games (queue 450), fit the `aram` table with the reduced feature list, same
   gates. Mayhem reads the `aram` table and sets `rough` with "ARAM model, augments not counted".
2. Posture in ARAM drops the objective options (no dragons or Baron); stakes are towers and
   inhibitors only.
3. Tests: Mayhem is always `rough`; no Rift-only features leak into the ARAM state.

Done when: an ARAM and a Mayhem recording replay with sensible curves and the UI shows the rough tag.
